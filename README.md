# Апгрейд — программа тренировок (PWA)

Личное веб-приложение с программой силовых тренировок v3: 2–3 тренировки в неделю, режимы на 60, 90 и 120 минут, три блока по 5 недель, журнал подходов и замеров, база из 1324 упражнений. Работает офлайн, ставится на телефон как приложение и синхронизирует данные через Neon (Postgres + Neon Auth + Neon Function).

Дни тренировок выбираешь сам, неделя программы закрывается по выполнению, циклом нагрузки можно управлять вручную. В журнале — графики прогресса, объёма и замеров. Данные выгружаются для анализа агентом, а его корректировки программы импортируются обратно с предпросмотром. Что дальше — в [ROADMAP.md](ROADMAP.md).

## Установка на телефон

- **iPhone:** открой сайт в Safari → «Поделиться» → «На экран „Домой“».
- **Android:** Chrome предложит «Установить приложение» (или меню ⋮ → «Установить»).

## Сборка

```bash
git clone --depth 1 https://github.com/hasaneyldrm/exercises-dataset vendor/exercises-dataset
python3 build.py        # нужны Python 3 и Node.js
```

Каждая сборка получает новую версию: установленное приложение покажет «Доступна новая версия» и обновится одной кнопкой.

## Данные и синхронизация

- **На устройстве.** Всё, что вводится, сначала пишется в `localStorage` (префикс `upg3:`), поэтому приложение работает офлайн и без входа.
- **Вход.** Экран входа открывается при запуске, пока вход не выполнен (можно «Продолжить без входа»), и сам — если вход истёк. Код на почту (Neon Auth, Managed Better Auth); cookie сессии хранятся в `localStorage` (префикс `upg3~`) и ходят к функции в заголовках — сторонние cookie не нужны, поэтому вход держится и в PWA на iPhone.
- **Долгий вход.** Сессия Neon Auth живёт 7 дней, поэтому сразу после входа устройство получает свой токен (`POST /device`, в базе — только его sha-256). Синхронизация идёт по нему; срок — 180 дней с последнего использования. Если токен отозван или истёк — откат на сессию Neon Auth, без неё — «Войди снова».
- **Синхронизация.** При каждом открытии и возврате в приложение, после изменений, при появлении сети и раз в 5 минут. Изменения копятся в очереди и уходят в базу, когда есть сеть. Журнал синхронизируется по тренировкам, замеры — по датам, настройки, цели, цикл, корректировки и правки программы (`plan`) — целиком, свои программы — по программе (`prog:<id>`), их места в цикле — `pos:<id>`, текущая программа — `curprog`. Конфликты решает время изменения записи.
- **Статус.** Облако в шапке показывает состояние (синхронизировано / идёт / в очереди / нет входа / ошибка); по нажатию — шторка: синхронизировать сейчас, проверить связь, где выполнен вход, выйти. Если входа нет или он истёк — баннер на «Сегодня».
- **Доступ.** API пускает только участников из таблицы `app.members`; почты из `MEMBER_EMAILS` добавляются туда при первом входе.
- **Правки программы.** «План → Тренировки»: изменённая тренировка хранится полной копией (`plan.s`), упражнения из базы — в `plan.x`; неизменённые тренировки берутся из `src/data.js`. Подробнее — в ROADMAP.md.
- **Несколько программ.** Встроенная «Апгрейд» (`main`) — правки в `plan`, как раньше. Свои — ключ `progs` = `{ [id]: { id, name, note?, base: null | "upgrade", days, wd, plan, created, at } }`: `base: null` — своя (с нуля или из шаблона: один блок, недели подряд, тренировки A–F), `"upgrade"` — копия встроенной (блоки и тренировки из `src/data.js`, поверх — свой `plan`). У своей дни недели — по буквам (`wd = { A: 1, C: 4 }`), у копии — списком, как у встроенной. Текущая — ключ `curprog = { id }` (нет — встроенная), переход — одна эта запись. Место в цикле: у встроенной — `cycle` (как раньше), у своих и копий — `progPos[id]` (синхронизация `pos:<id>`). Журнал своей программы — ключи `<дата>_<буква>@<id>` (и поле `prog`), у встроенной — `<дата>_<буква>`, так что записи программ с одной буквой в один день не смешиваются. Всё, что приходит из хранилища, с сервера или из файла, проверяется — битая запись не показывается.
- **Чередование и цикл нагрузки (v4.1, своя программа).** `rot = { pw, wd }` — тренировок в неделю меньше, чем в программе: идут по очереди, неделя закрывается, когда сделаны тренировки её очереди. У пункта тренировки `cyc` — шаги нагрузки (подходы, повторы, запас, % от максимума), каждый раз, когда тренировка приходит по программе, — следующий шаг; максимумы — `tm = { [exId]: кг }` в записи программы. Ничего дополнительно не хранится: шаг считается из места в цикле. Старая сборка эти поля не знает, но не теряет (`sanitize` хранит незнакомые поля) и показывает схему шага 1; правит старая сборка только обычную схему пункта — шаг 1 цикла при этом не меняется. Шаг считается «по выполнению»: сколько раз тренировка уже сделана в текущем заходе (с последнего «Начать заново»); в записи дня — номер шага упражнения (`st`). Смена «тренировок в неделю» и набора тренировок действует с текущей недели (`qa`, `rot.o`) и прошлое не переписывает.
- **Совместимость.** Данные выпущенной версии (`plan`, `cycle`, `settings`, журнал без `@`) работают без миграции; старая сборка на другом устройстве видит только «Апгрейд» и его записи (ключи `prog:*`, `pos:*`, `curprog` и дни вида `A@…` она пропускает).
- **Пока второе устройство на старой сборке:** корректировки агента, применённые в своей программе, старая сборка применит к «Апгрейду»; объём и регулярность «Апгрейда» там могут завышаться записями своих программ; удаление своей программы с упражнениями из базы переписывает `plan` «Апгрейда» целиком и может затереть одновременную правку на другом устройстве. После обновления сборка один раз забирает с сервера всё заново (сброс курсора), чтобы получить пропущенные старой сборкой программы.
- **Известное ограничение.** Запись программы синхронизируется целиком: при правках одной программы на двух устройствах сразу побеждает более поздняя (как у `plan`) — например, переименование на телефоне против правки тренировки на компьютере.
- **Резервная копия:** «Настройки → Сохранить копию в файл» (вместе с `progs`).

## Бэкенд (Neon)

`backend/src/index.ts` — одна Neon Function:

| Путь | Что делает |
|---|---|
| `/auth/*` | прокси к Neon Auth: cookie ↔ заголовки `X-Auth-Cookies` / `X-Auth-Set-Cookies` |
| `POST /sync` | отправка изменений и получение новых (по курсору `rev`); авторизация — `Device <токен>` или `Bearer <JWT Neon Auth>` (проверяется по JWKS) |
| `POST /device` | выдать устройству долгий токен (только по JWT, для участников); до 20 активных устройств |
| `GET /devices` | где выполнен вход: устройства, последняя синхронизация |
| `POST /device/revoke` | отозвать токен (текущий или по `id`) — при выходе |
| `GET /me` | кто вошёл и есть ли доступ |
| `GET /health` | проверка без обращения к базе |

**Беларусь и Россия.** Neon отвечает `403` на любые запросы оттуда (сайт GitHub Pages при этом открывается), поэтому без VPN нельзя ни войти, ни синхронизироваться. Для этого есть `relay/` — маленький прокси на Vercel во Франкфурте, который пересылает запросы в функцию как есть. Приложение ходит сначала туда, куда получилось в прошлый раз, а если ответа нет — по второму адресу (`api` и `relay` в `src/app-config.json`). Как развернуть — в `relay/README.md`.

Таблицы создаются функцией сама при первом запросе: `app.kv` (данные по пользователю и ключу), `app.members` и `app.devices` (токены устройств: хэш, срок, отзыв).

```bash
cd backend && npm install
neon link --project-id <id>              # один раз
neon deploy --env deploy.env              # в файле: ALLOWED_ORIGINS, MEMBER_EMAILS (не в git)
neon functions get api                   # invocation_url → src/app-config.json
```

## Личные заметки

Публичная программа (`src/data.js`) не содержит медицинских подробностей. Личная версия лежит в `private/data.private.js` (в `.gitignore`). `python3 build.py` сравнивает их и пишет `private/overlay.json` — эти поля загружаются в базу как запись `srv:overlay` владельца и после входа накладываются на программу только на его устройствах.
